Implementation plan · 17 October 2026 · MyDay / stream-chunk

Record a phone camera into timed chunks

A mobile web page takes the camera. A separate backend turns that feed into files and cuts them with video-chunker. Every client of the API gets the same folder of fixed-length MP4s.

Goal
Open a page on a phone, record the camera, and find fixed-length MP4 chunks in a folder on the server. Default length is 15 seconds.
Split
backend/ is an HTTP API with no pages of its own. frontend/ is one mobile client. Another page, script, or curl command can use the same API.
Cutter
In-process calls to video_chunker.chunk_video from the existing package. The API does not reimplement ffmpeg segmenting.
Stack
Python 3.11, FastAPI, uvicorn. The frontend is static HTML, CSS, and JavaScript. ffmpeg 5+ and ffprobe stay required, as they are for video-chunker.
Spec
This document is the spec. The two folders exist so the code has a home. The service is not written yet.

What done looks like

On a phone, the user opens one page, allows the camera, and taps Record. A preview plays. About every 15 seconds a new MP4 appears in the session folder. Tapping Stop uploads the last, shorter piece and marks the session complete. The page lists the files and can play them back.

On a machine with no camera, the same backend accepts a video file. A 62 second file becomes the same kind of folder: 15 second pieces and a short tail. That is the proof the API is not tied to the phone page.

This is a web page, not a native app. The lab session is a browser, and a store app cannot be demoed here. The phone opens the page in its browser.

What the chunker can and cannot cut

video-chunker takes one finished file. It probes the duration, plans cut points, and asks ffmpeg to write one MP4 per segment. It cannot read a camera, a socket, or a file that is still growing.

Two consequences follow.

  • The phone closes a recorder on a timer and uploads that blob. Each blob is a whole file, with its own header, so ffprobe can read it. Splicing raw MediaRecorder timeslices is not the plan: later Chrome slices are WebM clusters without a header, and later iOS slices are fragmented MP4. Byte-appending them does not make a file the chunker can trust.
  • A client that already has a long file skips the timer. It uploads the file once. chunk_video splits it. Same route, same folder layout.

Default mode is exact. Phone recordings are often VP8 or VP9 with Opus, and fast mode only copies H.264, HEVC, or MPEG-4 video plus AAC, MP3, or AC-3 audio. Exact mode re-encodes to H.264 and AAC so every client gets a playable MP4. Fast mode stays available as a session option for files that already match those codecs.

How a recording moves

One window, in order

StepWhoWhat happens
1ClientPOST /api/sessions with a chunk length. Default 15. The response carries id.
2Phone onlyStart MediaRecorder on the open camera stream. After 15 seconds of wall clock, stop it. The blob is one file.
3ClientPOST /api/sessions/{id}/media with that file as the body. A non-phone client may send a much longer file here.
4BackendWrite windows/window_NNNN.<ext>. Probe it. Apply the slack rule. Call chunk_video.
5BackendMove the chunker outputs to chunks/session_XXXX.mp4 so indexes continue across windows. Update session.chunks.json.
6ClientRead the JSON response and, on the phone, start the next recorder immediately. The upload of window N can still be in flight while window N+1 records. Only one upload is processed at a time per session; the client waits for the previous response before sending the next body, or the server queues them.
7ClientPOST /api/sessions/{id}/complete after the last blob. Further media posts return 409.

Recording and uploading overlap. The gap the user can see is only the time between stop() and the next start() on the same MediaStream, not the time ffmpeg spends encoding. Encoding happens on the server while the next window is already recording.

15 second windows and the slack rule

A recorder stopped at 15 seconds of wall clock rarely produces a file of exactly 15.000 seconds. The chunker, given a 15.3 second file and a 15 second cut, emits a 15 second piece and a 0.3 second tail. A folder full of those tails is hard to check by eye.

The backend applies one rule before it chooses chunk_s:

  • If the probed duration is at most chunk_duration_s + slack, call chunk_video with chunk_s equal to the probed duration. One upload becomes one MP4. Default slack is 0.75 seconds.
  • If the file is longer than that, call chunk_video with the session's chunk_duration_s. Full pieces are that length. The final remainder is its own file, which is the chunker's existing rule. Nothing is padded and nothing is dropped.

Session time is the sum of media durations. Each chunk row stores start_s and end_s on that clock, plus gap_before_s for the wall-clock pause before that window. The phone measures the pause from the previous stop() to the next start() and sends it as a header, X-Gap-Before-Ms. Clients that do not send the header store 0. A single long upload is one window with no gap.

Names

chunk_video names files from the input stem and always starts at 0000. The backend must not leave those names in the session folder or the second window will collide with the first. It stages each call in a temp directory, then moves the results to the next free session_XXXX.mp4 indexes.

HTTP contract

JSON for control, raw bytes for video. No cookies, no HTML, no redirect to a page. CORS allows the frontend origin from configuration. Default for local development is the frontend's origin. Tests call the API directly and do not need CORS.

Bind to 127.0.0.1 unless a host is set in the environment. There is no login in the first version. Do not put this on an open network without adding a token later.

POST /api/sessions

{ "chunk_duration_s": 15, "mode": "exact", "label": "phone" }

chunk_duration_s is optional and must be greater than 0. mode is exact or fast. label is a short display string stored in the session file, never used as a path.

{
  "id": "8f3a1c0b9e24",
  "status": "open",
  "chunk_duration_s": 15,
  "slack_s": 0.75,
  "mode": "exact",
  "label": "phone"
}

POST /api/sessions/{id}/media

Body is the file. Content-Type is video/webm, video/mp4, or video/quicktime. Optional header X-Gap-Before-Ms is a non-negative integer. The server does not trust a client filename.

The handler finishes cutting before it responds, so a client knows the files exist. ffmpeg runs in a worker thread so /api/health still answers. One session cuts one upload at a time.

{
  "session_id": "8f3a1c0b9e24",
  "window_index": 0,
  "probed_duration_s": 15.28,
  "split": false,
  "chunks": [
    {
      "index": 0,
      "file": "session_0000.mp4",
      "start_s": 0,
      "end_s": 15.28,
      "bytes": 2401133,
      "gap_before_s": 0
    }
  ]
}

split is false when the slack rule kept the upload as one piece, and true when the chunker cut it into several.

POST /api/sessions/{id}/complete

{ "id": "8f3a1c0b9e24", "status": "complete", "chunk_count": 4 }

GET /api/sessions/{id}

Returns the session fields plus the full chunks array from session.chunks.json. This is the document a frontend renders. It does not need to know about windows.

GET /api/sessions/{id}/chunks/{filename}

Returns one MP4. filename must match session_dddd.mp4 and must exist in that session. Any other name is 404. This is also the URL the phone uses as a <video src>.

GET /api/health

{ "ffmpeg": true, "ffprobe": true, "video_chunker": true }

ingest.py

This is the only module that imports video_chunker. The route handlers stay free of ffmpeg details so a second transport could call the same function later.

def accept_media(session_dir, upload_path, *, gap_before_s) -> list[ChunkRow]:
    info = probe(upload_path)
    chunk_s = session.chunk_duration_s
    if info.duration_s <= chunk_s + session.slack_s:
        chunk_s = info.duration_s
    staged = chunk_video(
        upload_path,
        stage_dir,
        chunk_s=chunk_s,
        mode=session.mode,
        overwrite=True,
    )
    return publish(session_dir, staged, gap_before_s)

publish assigns the next session indexes, moves the MP4s, deletes the stage directory, and rewrites session.chunks.json atomically (write a temp file, then rename). A crash mid-publish must not leave a half-written manifest. If chunk_video raises, publish does not run.

sessions.py

A session id is 12 hex characters from uuid4. The directory is data/sessions/{id}/. session.json holds status, chunk length, mode, label, and slack. A threading lock per id serializes media posts. Paths are resolved and must stay under STREAM_CHUNK_DATA.

State

Mobile frontend

One page in frontend/. Large type, one primary button, no hover-only controls. It is a client of the API and contains no cutting logic.

  • Preview: a muted <video playsinline autoplay> showing the camera. playsinline matters on iPhone, where a video otherwise goes fullscreen.
  • Record: request { video: { facingMode: "environment", width: { ideal: 1280 }, height: { ideal: 720 } }, audio: true }. 720p keeps encode time modest. Accept whatever the phone actually grants.
  • A second button flips facingMode between environment and user while not recording.
  • On Record, POST /api/sessions, then start a MediaRecorder. Prefer video/mp4 when MediaRecorder.isTypeSupported says so, otherwise video/webm;codecs=vp8,opus, otherwise video/webm.
  • A timer stops the recorder at chunk_duration_s. On the dataavailable and stop events, POST that blob if it is non-empty, then start a new recorder on the same stream. Send X-Gap-Before-Ms.
  • Stop ends the current recorder, posts the tail, then calls complete.
  • The page lists each chunk from the POST response and plays it from GET .../chunks/{file}.
  • A file input posts a chosen video to the same media route. That is how the page is tried on this VM, which has no camera.

The page talks to the API with relative URLs under /api when a dev server proxies them, or with an absolute base set in one constant at the top of app.js. It must not hard-code a session id, a folder path, or a codec choice for the saved files.

Serve the page from a real origin. file:// cannot use the camera, and a phone cannot use the VM's localhost. See Phone capture.

Any other frontend

A second client needs the contract and nothing from frontend/. This curl session is the acceptance test for that claim. It uses a short file generated in the test, not the workshop sample.

BASE=http://127.0.0.1:8765
ID=$(curl -s -X POST $BASE/api/sessions \
  -H 'Content-Type: application/json' \
  -d '{"chunk_duration_s":15,"label":"curl"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["id"])')

curl -s -X POST $BASE/api/sessions/$ID/media \
  -H 'Content-Type: video/mp4' \
  --data-binary @clip.mp4

curl -s -X POST $BASE/api/sessions/$ID/complete
ls data/sessions/$ID/chunks

A future page that does something else with the same cuts — a review tool, an uploader, a desktop browser — creates a session, posts media, and reads the chunk list. It should not need a change in ingest.py unless it needs a new transport. WebSocket streaming is out of scope; the file POST is the stable boundary.

Phone capture

getUserMedia only runs in a secure context: https:// or localhost on that same device. A page served as http:// from this VM will load on a phone and then fail the camera permission with no useful prompt.

Where you open itCameraHow to try the cutter
This VM's browserNo camera to use.The file input, or curl, against 127.0.0.1.
A laptop browser on localhostWorks if a webcam exists.Frontend on port 8766, API on 8765.
A physical phoneWorks only over HTTPS on a host the phone can reach.Put the page and the API behind the lab HTTPS ingress, or an SSH tunnel the phone does not need. Plain HTTP is not enough.

Build and test the API and the file-input path here first. Treat the phone camera as the last pass, after the folder layout is already right. iOS Safari needs iOS 17 or newer for MediaRecorder. If MediaRecorder is missing, the page shows the file input and says the live recorder is unavailable.

Ask for the microphone as well as the camera. If the user denies audio, record video only. The chunker already supports a file with no audio track.

The windows stay so a person can play the upload next to session_0000.mp4 and see that the cut matches. A later cleanup flag may drop windows/ after a successful publish. The first version keeps them.

Failures we already know about

Exact mode on a real file already failed once in this repo. A 30 second New York bike clip, cut at 5 seconds, produced six MP4s, then chunk_video raised CutFailed because the first piece was 5.071 seconds and the plan allowed about 0.067 seconds of slack. The manifest was never written. The later pieces, at 5.005 seconds, passed.

Do not build the service on top of that check as it stands. A phone file will miss the tolerance the same way, the API will return 500, and the user will see no chunk even though ffmpeg wrote one.

First task: loosen the exact-mode comparison in video-chunker so a cut that lands within a few frames still counts as the planned segment, and add a regression around a duration like 5.071 versus 5.000. Keep the failure for a chunk that is actually the wrong length, on the order of a whole second. The stream-chunk tests should then post a generated file and expect HTTP 200 plus a manifest.

Other cases the API must cover:

  • Empty upload, or a text body labeled as video: 400, nothing in chunks/.
  • Fast mode with a VP8 WebM file: the chunker rejects the codec. Return 400 with that detail and tell the client to use exact. The phone page always requests exact.
  • Disk full or ffmpeg missing: 500 from health and from media. Health is the check before a demo.
  • Two media posts at once for one session: the lock runs them in order. Indexes stay contiguous.
  • Complete with no media yet: allowed. chunk_count is 0.

Build order

Each task is done when its check passes. The boxes on this page are stored in this browser only.

1. Make exact mode accept a few extra milliseconds

In video-chunker, adjust the duration tolerance so the 5.071 versus 5.000 case publishes a manifest, and a chunk that is about a second off still fails. Run the existing pytest suite plus the new case.

2. Backend skeleton and health

Package under backend/, path dependency on video-chunker, GET /api/health reporting ffmpeg, ffprobe, and the import. Bind defaults as in the table above.

3. Sessions on disk

Create, read, and complete a session. Ids are generated. Status, lock, and path checks behave as specified. No video yet.

4. Media in, chunks out

Implement the slack rule and accept_media. A generated clip just over 15 seconds becomes one session_0000.mp4. A generated clip of about 47 seconds becomes four files. Manifest timestamps match the probe.

5. Download and errors

GET a chunk by the safe filename pattern. Cover 400, 404, 409, and 413. A failed probe leaves chunks/ empty.

6. Prove a non-browser client

The curl sequence in this plan, pointed at a generated MP4, writes the session folder. No file from frontend/ is involved.

7. Mobile page

Preview, record, stop, flip camera, list chunks, play a chunk, and the file input. The timer closes the recorder at the session length. The page uses only the HTTP contract.

8. Phone pass

Open the page on a phone over HTTPS. Record past two cut points. Confirm the folder has two full pieces and, after Stop, a tail, and that each file plays. If HTTPS is not available yet, record that the VM file-input path passed and the phone camera is still blocked.
